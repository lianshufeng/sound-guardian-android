# 红糖主动关怀开发计划

编制日期：2026-10-17。本文覆盖本地关怀、统一回复、数据保留与远程扩展契约；是开发计划，不代表业务能力已经实现或启用。

场景依据：[72 个关怀候选场景](care-scenarios.md)。该清单包括语音关怀、表情回应和不打扰条件；本计划分别安排，不把所有场景都做成自动播报。

## 1. 交付目标和边界

1. 本地事件、时间、天气及有效情绪证据可以产生关怀候选，由统一策略决定是否执行。
2. 同一套关怀执行器支持 `NOTICE`（播报后结束）和 `ASK`（播报后等待回复）。
3. 每次关怀有唯一 `careId`；本地和未来远程都使用同一请求、会话、结果和取消契约。
4. 支持用户开关、作息、勿扰、冷却、稍后、拒绝及有界存储，不反复打扰。
5. 本阶段实现本地闭环，远程只保留一个通用调用方法及结果回调；以后通信层直接调用该方法。服务端、网络连接、推送、登录、联系人通知及远程上传均属于后续阶段。
6. 复用现有 YAMNet、SenseVoice、VAD、唤醒、BehaviorEngine 和 SpeechPlayback。文字关怀先用有限规则及本地话术，不以接入 LLM 为前提。
7. 共享声音模型、标签、事件规则及算法仍在 `core/`；红糖的作息、偏好、关怀流程和存储在 `anlan/`。原 App 保持既有产品行为。

## 2. 实际基础与必须补齐的能力

| 能力 | 已有基础 | 本次开发项 |
|---|---|---|
| 声音与事件 | 521 类输出，18 类事件规则、事件历史与相对 dBFS | 事件窗口、组合证据；按需在共享层补其他声音规则并校准 |
| 文字与情绪 | SenseVoice 分段中文、情绪、声音事件；VAD；SpeechInput | 关怀所属倾听窗口、完整回复聚合、有限反馈意图和超时 |
| 天气 | 地区、未来约 4 小时天气、温度、体感温度；主屏可见时更新 | 与页面解耦的有效快照，受限后台需求更新；过期、缺失和地区切换处理 |
| 时间与互动 | 系统时间、唤醒、触摸、表情与播报状态 | 用户作息、勿扰、任务计划和可打扰性判断 |
| 播报 | 单一 SpeechPlayback，真实播放状态、字幕及取消 | 普通播报的关联完成回调、careId 贯穿、关怀执行与取消语义 |
| 数据库 | SQLite events.db；按数量清理事件 | 增量迁移、关怀请求/结果、计划、反馈可选保存、清理与容量约束 |
| 关怀接口 | CarePolicy、CareRequest、CARE 来源占位 | 扩展成可承载上下文、两种模式、结果和来源的稳定契约 |
| 高优先级事件 | 会中断并拒绝所有播报 | 为安全提醒定义受控播报资格，解决持续警报反复取消自身的问题 |

默认不开启持续陪伴，不隐式增加全天文字或情绪分析。ASK 执行期间才临时使用所属倾听窗口，结束后恢复原模式。

## 3. 统一请求、结果与远程预留

### 3.1 统一请求 CareRequest

现有类型最小扩展，必要时将数据类型提取为红糖层独立类，不在 core 放产品关怀策略。

| 字段 | 约定 |
|---|---|
| schemaVersion | 契约版本，初始 1 |
| careId | 每次关怀唯一 UUID；不能用场景名或 eventId 代替 |
| 调用来源 | 本次不设计通信来源枚举；调用方自行保留关联，来源不授予特殊优先级 |
| scenarioId | 稳定场景标识，例如 cough.repeated；关联下文 S02 |
| eventId | 可选，触发该请求的共享声音事件 |
| mode | NOTICE / ASK；用枚举表达是否等待回复，避免再维护冲突的布尔字段 |
| text | 本次播报文字，字幕使用同一文字 |
| priority | NORMAL / IMPORTANT / SAFETY；SAFETY 只能由受控策略授予 |
| createdAt / expiresAt | UTC 毫秒；请求在过期后不得开始播报或被重启补播 |
| replyTimeoutMs | ASK 的答复等待时间；NOTICE 固定为 0 |
| dedupeKey | 可选，用于同一事件/计划周期的业务去重，不替代 careId |

提案默认：ASK 等待 20 秒，允许范围 5—60 秒；单请求文字不超过 300 个 Unicode 码点。数值放在红糖关怀配置中并由真机试用调整，不散落到业务类。

上述过期时间限制尚未执行的候选请求；已开始的 ASK 由会话超时及最大时长约束，不因调度延迟偷偷重置预算。所有字段校验在提交时完成，非法请求返回明确原因。

### 3.2 执行入口与反馈契约

建议提供如下领域接口，具体命名可在实现时按现有结构微调：

```java
CareSubmission submit(CareRequest request, CareObserver observer);
boolean cancel(String careId, CareCancelReason reason);
CareSnapshot get(String careId);
void observe(String careId, CareObserver observer);
```

- `CareSubmission` 明确返回接受、已有同请求、忙碌、关闭、过期、不支持或参数非法，不能返回后静默丢弃。
- `CareObserver` 接收不可变阶段事件及唯一终态结果；不在持锁或采集线程中调用外部消费者。
- 同一 careId、相同内容重复提交，只返回已有状态，不再次播报；同 ID 不同内容拒绝为冲突。
- 去重与结果查询受有效期和记录保留窗口约束；清理后查询明确返回 NOT_FOUND，不承诺无限期记住 careId。未来远程协议须限制投递有效期，并为该期限设计有界去重凭据。
- 新观察者可以读取已有终态；终态写入只成功一次，通知必须可去重。进程崩溃不承诺回调恰好一次，调用方通过持久状态和结果标识恢复查询。
- 普通请求忙碌时不能简单替换当前 ASK。初始最多 1 个活动关怀和 1 个待执行关怀；额外请求明确返回 BUSY。高优先级抢占须先终结旧会话。
- 用户自设计划不是无限待播队列；计划项到期后也要校验有效期、勿扰和当前会话，再提交。

统一结果至少包括：

| 字段 | 约定 |
|---|---|
| careId | 唯一关联本次关怀；调用方自行关联以后通信层的请求 |
| resultVersion | 初始 1，支持未来结果格式扩展 |
| status | COMPLETED / REPLIED / TIMEOUT / CANCELLED / FAILED / REJECTED / EXPIRED |
| reason | 细分如 PLAYBACK_FAILED、INPUT_FAILED、SERVICE_STOPPED、INTERRUPTED、BUSY、USER_DISABLED 等 |
| replyText | 成功收到的完整回复；默认只在内存和当前回调中提供 |
| segments | 按顺序保留各次识别的文字、情绪、语言、声音事件和耗时，不编造整句情绪 |
| replyIntent | OK / NEED_HELP / DECLINE / SNOOZE / OTHER / UNKNOWN 等有限解释；保留原文，不把未知解释成同意 |
| startedAt / completedAt | 执行与终态时间；内部持续时间使用单调时钟 |
| replyStored | 是否保存了回复文本，查询接口应明确区分未保存与没有回复 |

NOTICE 真实播报完成返回 COMPLETED；ASK 收到有效回复返回 REPLIED。用户说“不用”仍是成功收到回复，replyIntent 为 DECLINE，不等同于系统取消。没有讲话是 TIMEOUT，识别失败是 FAILED；不得相互冒充。

### 3.3 远程只预留可调用方法

统一提供 `Care.submit(CareRequest, Care.Listener)`、`Care.cancel(careId)` 与 `Care.query(careId, callback)`。未来通信方式确定后，消息接收方直接调用 submit，通过同一 careId 的结果回调拿到语音文字、情绪等信息。方法不区分本地或远程，也不新建远程入口、适配器或服务。

通过普通调用方测试验证该方法的关怀执行、重复请求、回复和取消。本阶段不设计网络协议、来源权限、传输队列和上传逻辑；不积累“以后上传”的回复。

## 4. 会话、播报和回复处理

### 4.1 状态流程

```text
提交 → 校验/去重 → 等待可执行 → 准备 → 播报
                                         ├─ NOTICE → 完成
                                         └─ ASK → 尾音抑制 → 等待回复 → 回复完成/超时
任一非终态 → 取消/失败；每条路径均需写入明确终态
```

超时从真实播报结束、尾音期完成且 SpeechInput 实际开始接受本会话输入后计算。不能从 submit、开始合成或播放开始计算。播报失败不能继续打开回复窗口。

### 4.2 倾听与分段

- 同一时间只有一个负责收集回复的关怀会话；careId 之外，再持有服务代次、播报请求 ID 和输入会话标记。
- 保留唯一共享 PCM；不新建录音器。播报准备、播放及尾音期继续暂停文字情绪，YAMNet 守护不停。
- 当前普通交互无讲话约 4 秒结束；ASK 必须获得独立的有界等待预算，不能还没到 replyTimeoutMs 就被普通窗口关闭。
- SpeechInput 当前逐片段回调，不能把第一段当成完整答案。聚合属于本次会话的片段，在讲话自然结束后形成一次回复。
- 首版每次 ASK 收集一轮答复，原文最多 1,000 个 Unicode 码点、完整讲话最长 30 秒；到达边界明确返回截断或超限原因，不能静默漏字。VAD 和模型分段参数仍只维护在 understanding 配置。
- 等待截止前已开始的有效讲话可获得最多 8 秒的收尾识别宽限，另受回复总时长限制；不因噪声反复延长。具体数值统一配置并验收。
- 无法确定完整性、队列过载、采集断流和识别异常须返回 INPUT_FAILED 等结果，已收到的片段不能冒充完整答复。
- 长回答可以先完整回调给调用方；本地反馈解析只处理明确意图。多轮开放对话暂不实现，不能因为听到“需要”就无限追加问题。
- 会话完成或取消后，撤销定时器、输入回调、所属播报和待执行动作，恢复用户原有倾听模式。旧片段和异常不得影响下一个 careId。

### 4.3 播报接口与抢占

为 SpeechRequest 增加关怀关联信息，并为普通 speak 增加明确的关联完成/取消/失败观察能力，复用现有 SpeechSession 与真实播放回调。保留既有调用兼容，不借用 eventId 存 careId，不为了拿回调绕到第二套播音实现。

普通提醒等待说话间隙；直接唤醒、明确新交互及高优先级事件怎样打断 ASK，须有显式原因和可见状态。活动中的持续警报按事件 ID 去重，只允许符合来源和事件关联的安全提醒有限播放；不能在每帧检测到同一警报时再次取消自己。

安全事件优先级和 TTS 内容必须共同审查，不能允许外部请求自行声明 SAFETY 绕过限制。所有字幕继续按同一真实播放请求显示。

## 5. 本地数据、清理和设置

### 5.1 数据结构

首选沿用红糖现有 SQLite events.db，通过版本迁移增量建表，不引入另一套数据库框架，也不重建已有 events 表。需补现有 onUpgrade 的迁移路径。

| 表/存储 | 保存内容 |
|---|---|
| care_records | careId、来源关联、场景/事件 ID、模式、阶段、终态、原因、时间、有限回复意图、可选回复文本；careId 唯一 |
| care_schedules | 有界用户计划、当地时区策略、下一次执行时间、临时推迟/跳过和启用状态 |
| care_cooldowns | 有界场景/事件冷却及当前频率窗口，防止重启后连续提醒 |
| SharedPreferences | 总开关、分类开关、作息、勿扰、隐私选择及少量稳定偏好 |

关怀及对话文字自动保存，最多保留3天，不再提供保存开关；录音及全天倾听转写不保存。未来远程回传仍需独立授权。

### 5.2 建议的初始保留上限

| 数据 | 保留提案 | 触发清理 |
|---|---|---|
| 已有声音事件 | 保留现有约 300 条清理策略，保护活动事件 | 有变化保存时；原行为不因关怀表迁移改变 |
| 已结束关怀记录 | 最多1,000条且最长3天，先达到的限制先执行 | 写入、服务启动和低频维护 |
| 回复原文 | 最多300条且最长3天；每条最多 1,000 码点 | 写入、查询和维护 |
| 用户计划 | 最多 100 个有效计划，超限明确拒绝 | 创建、删除和完成时 |
| 冷却记录 | 按配置窗口过期，最大 256 个键；不把无限 eventId 长期保存 | 更新和维护时 |
| 内存关怀队列 | 最多 1 个活动和 1 个待执行请求 | 提交即做容量判断 |

提出 16 MiB 的关怀逻辑数据预算，统计请求文本、可选答复和记录负载；超限先清理过期/最旧终态，仍不足则暂停非必要持久记录或拒绝新关怀并报告 STORAGE_FULL。活动记录、计划和业务结果不能静默丢失；未能完成必要事务时不开始该关怀。

16 MiB 不是整个 SQLite 文件的硬上限；索引、页面、日志及已有事件另有开销。监测实际数据库和日志文件，采用空闲时受控维护，不能每次写入都 VACUUM 或在采集线程做清理。容量测试同时观察逻辑记录量、文件增长和多轮清理后的复用，不能承诺删行就立刻缩小文件。

若已经开始的关怀在写终态时遇到存储故障，仍须在内存中结束会话并通知调用方，额外报告持久化失败，不能继续等待或重复播报。数据库故障不停止现有 YAMNet 守护和警报表情。

重启后把未完成关怀标记为 CANCELLED/PROCESS_RESTART，不自动重新播放；结果元数据可查询，未保存的答复不能恢复。计划恢复只执行仍有效的任务，过时计划不集中补播。

### 5.3 用户设置及可见反馈

- 主动关怀总开关；身体、情绪、作息、天气、家庭等分类开关。
- 作息、工作日/周末、午休、安静时段；临时“今天晚点”“暂停一小时”等明确操作。
- 全局及场景频率；提案普通自动关怀最多 3 次/小时、8 次/天，同一类冷却初始 60 分钟。计划提醒单独管理，不能被闲聊消耗额度；安全关注不套用普通额度，但仍限制同一警报重复播报。
- 默认先以表情回应；只有用户启用的场景才主动开口。等待回复时明确显示“正在听你回复”，超时后退出。
- 关怀记录页显示何时、什么原因、是否完成/超时；不保存原文时明确标记。支持清空关怀记录和关闭保存。
- 提供“稍后”“不用”“是电视”“停止关怀”等屏幕操作，语音识别不可用时仍可控制。屏幕确认作为带来源的反馈，不伪造语音识别结果。

## 6. 规则、上下文和参数归属

建议新增红糖 `assets/care/policy.json` 与 `assets/care/scenarios.json`，分别放全局预算/频率/会话默认值、场景启用条件/话术/输出方式；只在确有需求时拆更多文件。

上下文用不可变快照提供事件窗口、时间、有效天气、有效文字情绪、用户设置、播报和输入可用性。策略保持纯 Java、无网络和数据库副作用；候选不等于执行，执行前再次检查时效、取消和勿扰。

| 参数或算法 | 唯一维护位置 |
|---|---|
| 声音类别阈值、确认、结束与事件合并 | core 的 event_rules.json / AppConfig / EventEngine |
| VAD、SenseVoice 分段、线程与模型参数 | core 的 understanding 配置及适配器 |
| TTS 音色语速、流式分句与缓冲 | core 的 tts/config.json |
| 触摸及表情保持时间 | 红糖 behavior.json |
| 关怀场景窗口、频率、回复超时、候选有效期和数据保留 | 红糖 care 配置；用户偏好作有界覆盖 |

天气提供按需可用快照；保留地区与对应预报小时，地区变化废弃旧候选。当前短时温度变化可用已有小时数据；“比昨天冷”必须有额外历史数据，不能从当前温度推断。

模型标签扩展需逐项采样校准；当前运行时保留所有不低于 0.25 的有限值分类，展示仍受有界候选队列和过期限制；不能直接用该列表代替稳定事件确认，也不能为了关怀在红糖复制第二套共享事件引擎。

## 7. 分阶段工作包

以下按依赖顺序交付，每阶段完成相应验收后进入下一阶段。每个工作包均采用最小补丁，不整文件重写；不在本次计划阶段启动业务实现。

| 阶段 | 具体工作 | 主要文件/模块 | 完成标准 |
|---|---|---|---|
| P0 基线与契约定稿 | 固定当前可用能力、配置字段、反馈语义及场景分组，记录工作区已有改动 | 本计划、care-scenarios.md、现有接口 | 区分已实现/待开发；保留已有用户改动；默认参数明确 |
| P1 统一关怀契约 | 扩展 CareRequest；新增结果、观察者、取消原因及通用调用方法 | InteractionPorts、Care；必要的红糖独立数据类型 | NOTICE/ASK、本地与未来通信共用方法；重复请求和参数非法有确定结果 |
| P2 关怀会话闭环 | 实现 CareCoordinator；关联真实 TTS 完成、尾音、输入窗口、分段回复、超时及抢占 | SpeechPlayback、GuardianService、UnderstandingWorker、GuardianRuntime | 注入一条 NOTICE 和一条 ASK 可完整结束；原唤醒及守护正常；不串回复、不泄漏回调 |
| P3 存储与用户控制 | SQLite 增量迁移、清理、终态恢复；关怀设置、记录及停止按钮 | EventStore 或同库帮助类、ControlPanel、红糖 care 配置 | 旧事件保留；上限和过期有效；重启不重播；默认不存答复原文；关闭后取消所属任务 |
| P4 本地声音与共情关怀 | 接入不可变上下文、纯策略、去重、预算；现有事件与有效情绪的保守场景 | CareContext、CarePolicy 实现、EmpathyPolicy 复用、BehaviorEngine | S01—07、S09—16、S23、S41、S43、S47—48、S57/S59 可按清单执行或保持安静；不把表情场景强制变 TTS |
| P5 作息、天气和明确语义 | 用户计划和临时调整；天气有效性与页面解耦；有限回复意图和本地内容 | 关怀计划/天气接口、WeatherRepository、设置及本地话术 | S17—23、S25—32、S49—58、S60—64 的对应条件和反馈闭环；无数据可降级，计划恢复不过期补播 |
| P6 扩展共享声音规则 | 为喘息、鼾声、门铃、宠物、流水、家电、娱乐背景等逐项增加和校准规则 | core/event_rules.json、必要的共享解析/测试、两款应用资产验证 | S08、S20/S24、S29 的雷声分支、S42/S44—46/S48 有样本证据；两款应用重新打包验证 |
| P7 安全关怀调度 | 实现安全事件抢占、关联播报资格、去重和明确求助处理 | 统一关怀协调器、GuardianService、SoundEvent 调度、SpeechPlayback | S33—40 可执行；持续警报不无限打断自身；普通/模拟远程不能绕过资格；没有通信能力不声称已联系 |
| P8 集成与真机交付 | 场景回归、数据库压力、后台/重启、资源回收、公共方法调用及用户试用 | core/app/anlan 测试、验收文档 | 完成下文矩阵、两个 APK 和资产验证；明确记录设备、失败及未执行项 |
| F 后续扩展 | S65—72 的外部数据/硬件；真实远程传输、授权、离线结果回传 | 预留端口的后续实现 | 本次仅保留契约，不计入本地功能完成条件 |

P4—P7 的场景只能在其所需基础都完成后启用；阶段表中的交叉编号表示组合依赖，不是重复实现。例如 S20 需要 P5 的作息及 P6 的电视规则，S29 的天气分支可先于雷声分支完成。

可靠日程是独立验收项：首个进程内版本只保证服务运行时调度。要交付“系统终止进程后仍准点”的提醒，需要在 P5 适配目标 Android 的持久调度、权限、重启与厂商后台行为；未通过真机验证前不能作为可靠闹钟宣传。设备关机期间无法发声，恢复后仅处理仍有效的任务。

## 9. 必须覆盖的验收矩阵

### 9.1 契约和会话

- NOTICE 只在真实播报完成后成功；ASK 在真实倾听开始后计时，回复按 careId 返回。
- 分段中文完整且保序；讲话跨超时边界、噪声反复触发、长答复和过载均有有限结果。
- 重复提交、不合法请求、来源冲突、忙碌、关闭和过期都有确定回执。
- 新唤醒、用户停止、高优先级声音、服务停止/重启、低内存和 TTS/ASR 失败均结束旧会话，旧回调不能进入新请求。
- 未开启持续倾听时 ASK 仍能临时收答，结束后恢复关闭；持续倾听开启时也只能把本窗口的答复交给所属关怀。
- 用户说“不用”“稍后”“是电视”、未开口和无法识别分别处理；按钮反馈可用。

### 9.2 场景和上下文

- 72 项登记覆盖：P4—P7 可实现项分别验证触发/不触发；F 项显示为能力未接入，不产生假动作。
- 偶发/反复咳嗽、清嗓、婴儿哭、情绪连续/冲突、夜间讲话、短时降温、天气过期/错地区、同一事件重复与多事件合并。
- 多人、电视、音乐、不同说话人、距离和噪声；无声不当在家/睡觉/安全证据，响声不当真实心理状态。
- 勿扰、拒绝、推迟、额度、跨日/时区/系统改时及后台重启恢复；无数据不编造上下文。
- 安全提示抢占普通关怀，持续同一警报不无限重播，不能由请求来源绕过安全资格。

### 9.3 存储和远程占位

- 从现有数据库版本迁移后原声音事件完整；新版本不重建旧表。
- 超过1,000条/3天、回复300条/3天、容量预算、低磁盘、写失败、批量清理均有明确行为；活动记录不被删除。
- 关怀及对话原文自动保存最多3天，录音及全天倾听转写不保存；到期清理、清空、进程崩溃及重启结果与界面一致。
- 普通方法调用返回同一 careId 的文字、情绪和终态，重复调用不重复播报；本阶段不接入远程通信，不产生待上传积压。

### 9.4 构建、设备和共享边界

首次依赖准备按仓库规范执行 `tools/prepare-tts.ps1`（含唤醒）和 `tools/prepare-understanding.ps1`。实施后的完整检查在仓库根目录运行：

```powershell
./gradlew.bat :core:verifySharedAssets :core:verifyWakeWordAssets :core:verifyTtsAssets :core:verifyUnderstandingAssets :app:assembleDebug :anlan:assembleDebug :core:testDebugUnitTest :app:testDebugUnitTest :anlan:testDebugUnitTest
```

按改动运行相关 lint 与设备测试。共享规则或资产变化必须重新打包两款应用，校验 APK 资产 SHA-256、原 App 的 6 项共享声音资产和三个未启用目录的排除、红糖完整共享资产；资源变更还要检查实际 APK 大小。

目标 ARM64 真机验证动态中文真实可听、字幕同步、ASK 回复、冷启动、TTS/SenseVoice 回收后重新加载、持续守护与多引擎共存。记录加载/识别时延、内存峰值、CPU、温度及一小时运行情况；模拟器结果与真机分开，不沿用 INT8 TTS 历史测量结论。

验收报告明确列出通过、失败和未执行项。涉及共享规则需同时验证原 App 既有 YAMNet 与红糖行为，不能只验其中一个应用。

## 10. 首个可演示里程碑

先完成 P1—P3，并用三条可控输入演示：

1. NOTICE：“外面有些冷，出门记得添衣。”真实播报完毕，返回 COMPLETED。
2. ASK：“听到几声咳嗽，需要歇一会儿吗？”等待用户完整答复，返回 careId、原文和有限意图；不回答时正确 TIMEOUT。
3. 任意调用方使用同一 submit 方法发起 ASK，取得文字和情绪；重复提交不重播，以后通信层直接复用。

该里程碑通过后再按 P4—P7 接入自动触发场景，避免先开启大量主动播报而缺少取消、反馈和存储闭环。

计划的首批实现及实际验证记录见 [关怀接口与实施进度](care-implementation.md)，尚未完成的场景以该记录为准。
