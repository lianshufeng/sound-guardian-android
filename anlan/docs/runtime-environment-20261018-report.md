## 内存增长、释放和OOM分析

1. **起终点的+7.73MiB不构成泄漏证据。** 起点229.99MiB，首分钟升到238.59MiB，随后大多维持236—238MiB；没有每分钟持续累加。全窗口PSS线性斜率约+0.0041MiB/分钟，剔除起点后约−0.0431MiB/分钟。斜率只是本窗口描述，不能外推数小时或几天。
2. **稳定段对比不支持持续增长。** 第1—5分钟与第26—30分钟PSS中位数分别237.67和237.12MiB，下降0.55MiB；均值分别237.76和236.06MiB，后者受第29分钟短暂回落影响。Native已分配内存两组中位数103.7334和103.7344MiB，差约1KiB；没有明显累积。
3. **第29分钟的PSS下降不能当作大模型释放。** 15:24→15:25的PSS下降约6.12MiB，15:26又回到237.72MiB；这期间native已分配内存几乎不变。原始meminfo显示Dalvik Heap PSS约下降4.83MiB、art mmap约下降1.31MiB，符合共享页面计账/驻留变化等解释；没有证据把它定性为TTS或SenseVoice卸载。
4. **线程和页面对象没有持续累积。** 线程57—58，Activity始终1个，View数量42—51波动、起终点均42。Java已分配堆3.33—3.49MiB。线程或View快照正常不能替代堆引用分析，但未出现直接泄漏信号。
5. **系统余量充足但不是OOM保证。** MemAvailable最低约5.81GiB，SwapPss约5.2MiB且未持续增长。系统余量不能代表Java单进程堆限额、native连续分配成功或低端机安全。
6. **窗口前的大内存单独看待。** 14:53准备阶段PSS为1,206,654KiB（约1.15GiB）、native已分配1,107,217KiB；正式起点已降到235,507/105,544KiB，同PID。这个回落与重型资源释放一致，但缺少加载/释放的精确阶段证据，不能认定具体是哪一个模型，也不能将窗口前值算作本轮30分钟最大值。启动及动态语音的峰值仍是后续应重点补测的风险。

工作区`ResourceBudget`区分约4GB及以下的10秒空闲释放与普通档60秒，并用可取消重型作业许可限制TTS/SenseVoice并发加载计算；`LocalSpeechOutput`有短句PCM缓存、初始化结束释放和空闲释放；`UnderstandingWorker`在模型所属线程执行空闲释放。这些机制与当前约237MiB的低位驻留相容，但本轮没有逐模型加载计数，不能证明每一条释放路径都执行成功。TTS512MiB/SenseVoice320MiB准入估计仍未由本轮组合峰值校准，不能据此宣称避免OOM。

## CPU开销、运行状态与优化线索

环境音守护也需要持续工作。工作区实现中，唯一采集线程分发16kHz PCM；共享YAMNet输入15,600样本、步长7,680样本，即稳定输入下约每0.48秒一次推理；KWS消费共享PCM；普通内存档`FaceView`可约33ms刷新一次。稳定占用约三分之一个逻辑核心并不等于没有开销，也不能根据整机3.6%直接计算耗电。

15:29:09额外做了一次只读线程补采，**不计入上述半小时统计**。`top -H`短时记录出现RenderThread约10.7%、anlan-wakeword约7.1%、应用主线程约7.1%，同PID服务仍为前台服务。这个快照说明渲染、主线程和唤醒都有可见开销；采样区间短、存在工具取样偏差，不能当作半小时模块耗时分解。没有证据将全部CPU归因于YAMNet或新波浪效果。

建议优先顺序：

1. 用Perfetto/线程差分对相同设备、相同环境做1—2分钟低干扰对照，拆分UI、KWS、YAMNet和采集成本；先测再改，不直接削减唤醒PCM或更改声音模型步长。
2. 评估普通档静态/睡眠表情降低刷新率、触摸/过渡/明确交互保持较高刷新率的最小A/B。现有工作区普通档持续刷新是可检查点，节能效果尚未测量。
3. 将冷启动、动态TTS、连续唤醒、交互后回到空闲作为独立资源测试，检查native高峰是否回落，避免用环境音稳定段掩盖启动峰值。
4. 本轮没有证据要求改动模型或共享事件规则；报告未自动修改应用代码。

进程存活和前台页面不代表声音链路每一环都健康。采样没有保留KWS解码PCM计数、队列溢出、守护推理耗时、事件写库失败或当时录音静音状态的完整健康曲线，所以不能声称全程没有丢块、误触发、漏检或麦克风被静音。
