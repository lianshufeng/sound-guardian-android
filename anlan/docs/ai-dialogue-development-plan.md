# AI 对话接入开发与验收计划

## 播放前续说

唤醒/点击首轮从实际输入就绪后等待6秒，后续轮次保持3秒未开口退出；分别由`dialogue.json`的`wake_listen_ms`、`listen_ms`配置。原话轮识别后可先提交LLM并有界准备首段TTS，继续复用同一输入所有者及唯一PCM流，直到首段真正获准播放。疑似人声立即显示聆听表情及“正在听你说话 / 请继续说”，仅暂缓播放；SenseVoice返回含有效文字的Speech结果后，先缓存提交后新增的文字及片段，旧请求不按每个识别片段取消。补充话轮结束、识别排空并经过`continuation_silence_ms=1800`稳定期后，才统一作废旧请求代次、取消网络及未播草稿，将原话及本批补充合为同一用户消息重发。新增人声或有效文字使旧稳定任务失效；可多批补充，总文字、片段时限及会话总时限仍有界。未播草稿不加入已回复上下文，不重复保存为已完成话轮；明确停止、本地控制、失败及优先级中断仍可立即取消。

等待正文时显示“想一想”；超过`wait_feedback_ms=3000`显示“还在想，你也可以继续说”，收到可朗读正文并创建同一流式播报后显示“正在准备声音”。补充期间优先显示续说提示；无有效补充则恢复对应准备状态。反馈只使用文字，不额外播放“请稍等”或提前显示正在播报。正在等待网络、合成及排队期间不按首轮6秒/后续3秒的开口无声时限结束，仍遵守网络、输入、合成及会话总时限。长于稳定期的停顿可能形成新的提交批次，不能保证猜出用户还会继续说；实际播放后仍暂停输入。

无有效文字的片段在VAD及识别排空后恢复原回答，不因纯音量或VAD命中取消请求。原始Speech标签和文字不能证明是用户本人，电视对白仍可能误触发；不声称具备说话人验证。播放器在主线程、资源锁外调用`beforePlayback`；输入工作器原子确认无人声及待识别片段后关闭输入，首段才允许播放。首段合成可与轻量VAD并行，SenseVoice/TTS重型工作仍共用串行许可。实际播放及段间、尾音仍抑制输入，不支持边播边听。输入失败、过载、内存回收、结束、配置变更和高优先级事件使旧输入及请求失效。

本能力需区分状态注入、真实PCM识别、真实网络与物理麦克风/实际可听验收；历史测试不代表本次续说已验收。

状态：2026-10-18 已实施，验收进行中。本文前十节保留原开发和验收要求，实际执行状态见末节，不能将计划项当作已验收。接口范围为用户提供的 OpenAI 兼容服务；服务端远程关怀通信暂不实现。

## 一、目标与范围

打通“小安唤醒/关怀提问 → 统一倾听 → 本地语音识别与情绪 → 本地指令或 LLM → 流式本地 TTS → 有限多轮倾听”。保留现有声音守护、关怀开关、安静时段、限频、存储上限和唯一 PCM 采集。

- 仅安澜启用网络对话；不把应用配置、网络代码或对话业务放进 core。共享声音规则及模型不因接入 LLM 改动。
- 默认关闭 AI 对话。用户开启并配置后，只有明确唤醒、主动进入对话、或通过既有关怀准入的 ASK 回复可进入网络对话。
- 持续陪伴仍用于本地识别、共情和既有规则，不自动把旁人谈话或所有识别结果提交 LLM。
- 简单控制、本地数据问答及警报提示优先本地处理；固定通知和表情不必调用 LLM。
- 首版采用轮流说话。播放、提示音及尾音期间抑制语音输入和唤醒，点击停止可打断；不承诺边播边听或播放中喊“小安”打断。
- 提示用户在“我在”和就绪提示结束后讲话。“小安今天天气怎么样”一口气连说须单独测量；本期不以此作为已支持的无缝连续唤醒能力。
- 本期不实现电话、联系人通知、服务端远程通信、通用工具调用、长期记忆、可靠闹钟、开放式游戏引擎或专业健康诊断。

## 三、设置、持久化与网络协议

### 3.1 菜单 → 设置 → AI 模型

- AI 对话开关、Base URL、Token、模型名、测试连接、保存和清除。Token 默认隐藏，不回显到连接测试详情或日志。
- Base URL 明确填写 API 根地址，例如 https://example.com/v1；规范化尾斜线，避免重复拼接 /v1/chat/completions。模型名支持手填，不依赖 /models 必须可用。
- 默认 HTTPS；如需局域网 HTTP，提供显式选项和对应访问范围，不关闭 TLS 校验或默认信任任意证书。
- 连接测试使用少量文字和输出预算，验证鉴权、模型及流式正文；显示错误类别和耗时，不把 HTTP 200 或模型列表成功当作对话成功。说明会产生一次接口请求。
- 保存成功才反馈已保存。修改配置取消旧配置的活动请求，清除旧对话上下文；不让新密钥搭配旧地址。
- 普通字段存在应用私有设置中；Token 用 Android Keystore 支持的加密方案持久化。密钥无法解密时明确要求重新填写，不崩溃或悄悄使用空 Token。
- 强制停止、进程回收、重启和相同签名覆盖安装后应保留配置；卸载、清除数据或密钥失效不保证保留。当前应用 allowBackup=false，不承诺换机恢复。

### 3.2 OpenAI 兼容客户端

基线为 POST {baseUrl}/chat/completions，messages、model、stream=true 与 Bearer Token。按 SSE 事件解析 choices[].delta.content，分离 finish_reason、结束标记和错误。依据用户服务的实际兼容性确定输出预算字段，不假设所有服务都接受 temperature、max_tokens 或 max_completion_tokens，不默认要求工具调用、JSON 模式或 Responses API。

- UTF-8 字节、SSE 行和事件可能跨网络块；支持 LF/CRLF、空正文、角色块、心跳/注释、空 choices 统计块、未知字段及多事件同包。
- 只播报用户可见正文，不朗读 reasoning_content、工具参数或思考标签；跨片段的标签过滤必须有状态。未支持的工具调用明确失败，不执行模型生成的指令。
- 正常结束、内容过滤、长度截断、空正文、半途断流及协议损坏分别报告。连接断开不能伪装为完整回答。
- 网络线程不阻塞 UI、采集或模型工作器。单活动请求、有界网络块和待播文字，逐块读取并响应背压；取消关闭响应体和连接。
- 发生中断后不自动重发已经播出的回答，避免重复播报和重复计费；用户可重新发起。
- 不记录 Token、请求原文或完整响应。必要诊断记录脱敏错误、会话标记和分阶段耗时。

协议参考：OpenAI 官方 [Chat Completions streaming events](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events) 与 [Streaming API responses](https://developers.openai.com/api/docs/guides/streaming-responses)。兼容服务的扩展和限制以实际联调为准。

## 四、统一输入与 UI

两个入口共用以下状态：IDLE → PREPARING → PROMPTING（可选）→ CUE → LISTENING → RECOGNIZING → THINKING → SPEAKING/WAITING → 尾音 → 再次 LISTENING 或结束。

- 唤醒：确认唤醒 → 统一播报“我在” → 输入准备/短提示音 → 就绪后显示“我在听”。
- ASK：原规则通过准入 → 播报关怀问题 → 同一个输入准备/提示音 → LISTENING。
- NOTICE 不进入输入特效、不播放输入提示音、不主动续听。
- 输入会话预先绑定结果、准备模型；提示音及尾音完成后打开有效接收窗口并开始无回复计时。避免声音已提示、识别却未准备好。
- 原有真实播报、字幕、唤醒抑制及采集继续运行。提示音经同一播放调度/LocalSpeechOutput 输出，统一取消、音量和尾音处理；不创建页面播放器或第二套 AudioTrack。
- UI 保留脸部表情，在外围或下方绘制柔和光环；就绪呼吸、讲话时随真实音量轻微变化、识别/等待缓慢流动、播放跟随真实状态。音量只驱动动画，不当作情绪。
- 小字区分“准备倾听”“我在听”“正在识别”“想一想”和错误；不把加载中或提示音阶段显示为可以说话。
- 提供明显但简洁的停止按钮；播放时点击停止取消网络、待播段和所属会话，输入时点击结束停止倾听。活动页面重建不重复播放提示音或提问。
- 降低动画帧率、无效状态停止绘制；后台继续遵守现有前台服务策略。隐藏页面不残留触摸状态。
- 保留当前 VAD 基线，通过断句样本调整；一次用户话轮的片段按序聚合，只提交一次 LLM，不每个 ASR 片段发一次请求。

当前参数（集中在 `dialogue.json`）：唤醒/点击首轮输入实际就绪后6秒、后续3秒未开口即结束，单话轮最长30秒并保留8秒识别收尾宽限，单轮用户文字上限1000字；一场会话最长5分钟。准备、叮声及尾音不消耗无声等待时间，已经开始讲话不会被无声等待时限截断。关怀首轮请求已有 replyTimeoutMs 优先，仍保持原有关怀配置；会话总时长不能替代各阶段的独立超时。

2026-10-18唤醒回应取消600毫秒动画等待，识别准备可与缓存回应播放重叠；回应完成即交给统一输入控制器，不再叠加Service/Conversation/Care的独立尾音。最终650毫秒配置保留。网络等待时普通内存档可提前准备TTS，普通整句对话播报开始可准备下一轮识别；流式回答暂不提前加载ASR，重型计算共享单项许可，不能理解为全双工。数字PCM、本地时间回答与退出、缓存/提示音绕过繁忙合成的本轮结果见[性能验收](../../evaluation/interaction-performance-acceptance.md)；不沿用历史真实网络或真机验收结论。

## 六、提示词、上下文与动作

统一模板按三层组合：身份与表达规则、可信当前场景、用户消息和有限历史。提示词资产在安澜维护，版本可追踪；不在各场景复制。

核心模板示例：

> 你是小安，一个温暖、自然的智能守护音箱。默认用一至两句简短中文回答，通常不超过80字。先回应当前的话，不重复问候；需要了解情况时一次只问一个问题。用户要安静或结束时尊重他的意思。声音和情绪只作为不确定线索，不诊断、不猜原因。没有有效数据就不编造天气、时间或已执行动作。输出适合直接朗读的正文，不含Markdown、思考过程或动作旁白。

- 故事等明确请求通常 150—300 字，短段落；首版普通回复硬上限建议 160 字，故事硬上限 400 字，在完整句界结束。超出、网络截断和播放失败都保留真实终止原因，不能以静默丢字实现长度限制。
- 最多保留最近 6 个完整问答轮；请求所有文本字段合计最多 8000 个 Unicode 字符，场景摘要最多 1000 字，单用户轮最多 1000 字。超限先删最早完整问答；保留系统规则和当前用户信息，仍超限则明确拒绝/提示缩短。字符预算不能冒充精确 token 数；服务返回上下文超限时再缩减历史并明确报告，不能循环重试。
- 按需加入时间/时区、有效天气及更新时间、触发声音及事件 ID、原始情绪标签、关怀问题和本轮回答；不上传全部历史或音频。声音事件与情绪不作为用户亲口陈述，用户否认后尊重更正。
- 当前天气问答、时间、晚点睡、关闭关怀、稍后、再见等确定能力由本地路由执行并返回真实结果；首版不依赖模型工具调用。
- 不把任意模型文字当成本地控制命令。模糊的设置请求需要明确澄清，不让“假装已经设置好”成为成功状态。
- 历史只纳入确认完成的用户话轮和实际成功播放的助手段；取消后不把未播放的生成内容当成用户已经听到。保留部分播放标记，避免续聊引用未听到内容。
- 用于模型请求的对话上下文仅在内存保存，新会话、切换配置、关闭AI、服务终止时清除；终态历史记录自动保存最多3天，不作为跨会话长期记忆，不生成永久摘要。

## 七、流式播报、异常与抢占

- 复用 SpeechPlayback.openStream，扩展必要的会话关联字段，不新建合成器；保留固定语速、有限分句、当前段及最多一段预合成。
- 一次 LLM 正文流对应一次流句柄。增量进入有界缓冲；append=false 时保留整片段，暂停读取并等待重试；单片段先拆至允许大小，等待有上限。网络积压不能改成无界字符串。
- 字幕由真实开始播放的段驱动；模型首字到达不等于开始说话，网络等待和 TTS 段间 WAITING 都不假装播放。
- 连接 10 秒、首正文 20 秒、流中空闲 15 秒、单请求总计 60 秒作为初始建议值；均可集中调整。尽量在首正文到达后才打开 TTS 流，避免与原有流输入超时冲突；整场时限仍覆盖排空和播放。
- 401/403、404/模型不可用、429、5xx、无网、DNS/TLS 失败、首字超时、流截断、空正文、TTS 错误、输入超载及低内存都有独立原因和短中文提示。同一故障只提示一次。
- 已播出部分文字后失败，不完整重播；标记中断，结束或由用户主动重试。错误提示本身仍经唯一 SpeechPlayback，避免回调递归导致反复播报。
- 优先级：本地高优先级声音处置优先；其次用户显式停止/新会话；再是已准入关怀和普通对话；被动表情不抢占。已有安全提示许可不能被通用对话继承。
- 取消同时停止所属网络、输入、提示音和待播段，撤销延迟任务；服务重启、权限撤销、关闭 AI、配置变更、低内存、采集断流分别返回原因。

## 八、关怀 ID、后续结果与数据清理

保留 Care.submit/query/cancel/respond 的已有一轮语义：NOTICE 播放完成，ASK 首轮收集完成立即产生原有 Care.Result，LLM 故障不能把已成功收集的用户回答改成失败。

- 每次后续对话使用 sessionId，每轮 turnId；关怀来源关联 careId、scenarioId、eventId。通用唤醒也有 sessionId，但不伪造 careId。
- 新增通信无关的后续订阅/查询入口（例如 Conversation.observe/query/cancel），可按 sessionId 或 careId 取得关联会话状态与结果；未来通信只调用这些方法，本期不连接服务端。
- 结果区分首轮关怀反馈、后续用户转写/情绪片段、AI 生成正文、实际播放段及终止原因。时间、来源和顺序可追踪；终态只发一次。
- Care.cancel 仍针对其未结束的关怀；首轮结束后，用 Conversation.cancel 取消关联续聊，不让既有终态再次变化。查询中途状态和最终结果分开，不篡改 Care.query 的历史含义。
- 关怀及对话元数据、用户回复和AI正文自动保存，最多保留3天；不保存录音及全天倾听转写。实时回调与历史查询仍区分原始正文和实际播放内容。
- 关怀及关联对话不提供保存开关，遵守当前1000条/3天记录、300条/3天正文和16 MiB容量预算；多轮新增片段还须有条数/字数上限，不以一条记录绕过容量。
- 数据库增量迁移、不清空既有事件；维护任务同时清理新增记录。AI请求内容离开设备的说明与本地3天保留策略分别说明。

## 九、验收分层与样本

所有报告记录代码版本、APK 哈希、设备型号/Android/API/ABI/RAM、配置和提示词版本。以下四种证据分别命名，不能互相替代：文字/事件注入、数字 PCM 注入、真实网络模型、物理麦克风及可听播放。

### 9.1 确定性单元与集成测试

1. 配置保存/读取、异常密文、URL 拼接、脱敏、保存失败、配置切换与取消。
2. SSE：逐字节拆包、中文多字节边界、多事件同包、CRLF、心跳、空块、统计块、停止/长度/过滤终止、无结束标记断开、损坏 JSON、超大事件及未知字段。
3. 正文过滤：reasoning_content、分片思考标签、Markdown、空正文、非正文工具块不会发声；纯正文顺序和内容不被破坏。
4. 状态机：就绪才计时、提示音不进入识别、VAD 多段只提交一次、首轮回复/继续聊、无回复、输入太长、结束、警报抢占、旧回调、服务重启、配置变化及低内存。
5. 上下文：轮数、字符总预算、单轮上限、天气新鲜度、原始情绪、历史裁剪、未播放内容不进入已听历史、跨会话不串线。
6. 背压与播放：上游快/慢、拒收重试、暂停超时、结束排空、取消、替换、TTS 失败；无重复、漏读、无界队列或无限等待。
7. 关怀：原入口兼容、ID 去重/冲突、首轮终态不被后续失败覆盖、关联查询、远程同方法调用模拟、隐私关闭、迁移、按时间/数量/容量清理。

样本在实施时随测试生成并标明来源：

- 不少于 40 条文本场景用例，覆盖自由聊天、固定控制、天气缺失、更正情绪、拒绝、求助、故事、放松和安静结束。
- 不少于 20 组可重放 SSE 正常/异常响应，至少包含快流、慢流和中途断网；固定随机种子及预期正文哈希。
- 不少于 24 条中文合成 PCM，采用至少两种可用声线/语速，覆盖唤醒后问话、多片段、长停顿、近似称呼及控制语句；叠加可追踪来源的低幅噪声用于鲁棒性测试。统一为现有输入采样契约，保存生成脚本、文字、时长、格式与 SHA-256。
- 情绪策略用带原始标签的结构化结果注入做确定性验证；不能把合成音色当作真实情绪准确率证明。真人情绪只记录模型标签和人工听感，不宣称心理状态。
- 注入 PCM 必须走实际输入适配/识别链路，不能直接写出预期转写后声称 ASR 通过；直接方法测试独立标注为业务逻辑测试。
- 样本只进入测试资产或 evaluation，不进入正式 APK；生成语音不替代真人远场验证。

### 9.2 模拟器端到端

使用正式输入、会话和 SpeechPlayback 入口：模拟器 + 本地可控 SSE 服务，完成唤醒/关怀 → ASR → 流式网络 → TTS → 字幕 → 续听及查询。逐条验证每个已接入场景的正向、拒绝/超时和开关负向路径；未接入场景验证没有额外网络调用。

Android 9/API 28 作为既有旧系统重点，补最低支持 API 26 和当前开发 API 的构建/运行检查；记录使用的 ABI。模拟器性能只用于回归对比，不作为目标真机性能结论。

### 9.3 真实接口与表达质量

提供服务地址、密钥和模型名后，在正式客户端执行：

- 保存/读取与真实连接测试；普通对话、至少 5 轮上下文、关怀后续聊、故事和天气依据。
- 覆盖 401、错误模型、限流/超时等可控负向案例；不能安全诱发的异常改由模拟服务覆盖并标明。
- 固定文本集逐条跑真实模型，人工核对温暖、简短、一次一个问题、尊重结束、不乱报天气、不把情绪当诊断、不声称已外呼/已设置。
- 所有控制和隐私约束必须通过；普通答复至少 90% 达到默认 80 字内且无需硬裁剪，硬上限由本地保证。随机性质量问题保留原用例和版本，不能只挑成功样本。
- 单次输出前期失败与部分播报后失败均能恢复；网络模型请求取消后不会重新开口。

### 9.4 真机物理麦克风与实际播放

至少覆盖旧 Android 目标设备及当前 ARM64 真机；旧设备若只有模拟器，明确标成缺少旧系统真机验证。4 GB 及以下目标设备单列，未提供时不得宣称低端性能已通过。

- 实际喊“小安”，等就绪提示后真人问时间/聊天，确认能听见真实回答；接续至少 5 轮后结束。
- 用调试入口发起真实 ASK，再由人对物理麦克风回答，确认与唤醒相同的输入效果、提示音、识别和结果查询。另用实际声音检查关怀触发；事件注入不能替代声学触发验收。
- 建议至少两位说话者，在安静与电视背景下分别测试 0.5 米/2 米距离，每组至少 5 次；记录唤醒成功、话轮识别和完整交互成功三个指标，不只记录总成功数。
- 检查提示音/自身 TTS 不被识别成新请求、不自唤醒、无输入时不反复叮；识别加载时 UI 不提前提示可说话。
- 点击打断、输入超时、结束后再次唤醒、来警报中断、后台/回前台、权限撤销、服务停止重启、低内存释放后重载。
- 人工确认是否可听、字幕与声音一致、故事段落顺序；播放进度回调不等于可听验收。
- 近讲合成样本、扬声器回放与真人远场结果分别报告；一口气唤醒加问句及播报中讲话作为边界案例，不隐瞒丢失内容的限制。

### 9.5 性能与稳定性

同设备、相同构建方式、相同声学/网络条件对比接入前后基线，冷启动和热会话分开。验收采样覆盖守护空闲、唤醒、ASR、网络等待、首段合成、持续播放、续听、退出和模型空闲释放。

- 时延分别记录：用户话音结束→识别完成、请求→首正文、首正文→首段真实播放、话音结束→首个可听回答、取消→声音停止。每种冷/热条件至少 10 次，报告中位数、P95 和最大值，不把网络延迟计成 ASR 或 TTS 耗时。
- 资源记录总 PSS/RSS、Java/native 堆、线程数、队列水位、CPU 采样区间及核数口径。阶段快照和周期采样峰值分开，不宣称绝对峰值。
- 先完成 100 个自动会话替换/取消循环，再做不少于 30 分钟包含聊天、守护、关怀和空闲的混合运行；退出并等待设备预算的模型释放期后再次采样。
- 硬性要求：无崩溃/ANR、无采集线程阻塞、队列不超配置、无旧回调污染、无持续增长的会话/线程/缓冲、关闭 AI 后不再发起模型请求。
- 性能门槛先以同机基线量化：网络/状态管理本身的空闲 PSS 增量目标不超过 20 MiB、空闲 CPU 增量目标不超过一个逻辑核的 2 个百分点；用相同模型加载状态连续三个窗口复测，超出则定位。ASR/TTS 峰值与冷加载另列，不拿此增量目标掩盖其资源占用。
- 第一轮实测后按目标设备确认可接受的整链时延，计划不虚构“必定两秒响应”；如果低端设备重载过慢，应如实列为限制并优化，不以模拟器替代。

## 十一、竞品参考与产品判断

本计划参考了 Google Home/Gemini 的续聊、Amazon Alexa 的自然语音设计以及 ElliQ 的主动陪伴方式：

- Google 的续聊在回答后保留有限输入窗口，用灯光/麦克风状态提示正在听，静默一段时间或说“停止/谢谢/我完成了”等结束；对闹钟、媒体和高优先级活动不强行续聊。
- Alexa 的语音设计强调在打开输入前立即说清楚问题，避免用户在设备还未准备好时讲话；回答必须适合听，而不是照搬书面长文。
- ElliQ 把主动关怀设计成短时、可感知的 check-in，无人回应就停止倾听，并把隐私开关和用户授权作为远程分享前提。

这些做法与“智能守护音响”定位一致：守护逻辑仍由本地规则掌控，LLM 用于温暖的短回答和有限续聊；主动关怀要少打扰、可拒绝、可查询；安全事件、提醒和实际动作不能等待模型或由模型虚构完成。

本次提供的服务配置可作为联调 profile：OpenAI 兼容 Chat Completions、模型 `qwen3.7-flash`、流式正文、请求中通过服务扩展字段关闭思考。该模型及 `enable_thinking=false` 的用法以阿里云官方文档为准；此扩展不是通用 OpenAI 字段，客户端应按配置能力发送，不能写死到所有模型。Token 只允许在本地运行时输入，不进入本文件、源码、资源、日志、APK 或验收附件；本轮没有把用户提供的 Token 保存到仓库。凭据曾在对话中暴露，正式使用前应在服务端撤销并重新生成。

## 十二、2026-10-18 实施与验收记录

### 已实现的入口

- 一级菜单 → AI模型（位于“关于”上方，已移出“设置”，返回键回到一级菜单）：默认字段为空、默认关闭；页面使用“服务地址”“访问密钥”“模型名称”“优先快速回答”等使用提示，不展示发布包、加密实现或流式正文等技术说明；保留文字发送与不上传录音的隐私提示。实际仍使用HTTPS API根地址、Keystore加密Token、关闭思考扩展、提示音开关、保存/清除及真实流式连接测试。
- 喊“小安”后回应“我在”，或点击左上角“安澜”（已移除独立“说话”按钮），首轮通过同一个 InputSessionController 准备 SenseVoice，跳过额外叮声，尾音保护使用dialogue.json的wake_tail_ms（150毫秒）；后续轮次和Care ASK仍按提示音开关播放150毫秒880Hz短促叮声，再等待tail_ms（650毫秒）。实际解除输入抑制并启动输入后才显示“请说话”，首轮6秒、后续3秒静默退出保留在后台，界面不显示倒计时。底部白蓝渐变波浪的绘制区由56dp增至72dp，提示区同步避让；取消圆角条块、边框及小光环。波浪两侧低、中部高，等待时平滑呼吸，实际倾听并检测到讲话时按共享PCM短时音量起伏；准备、叮声、识别及播报时仅低幅流动。原有 Care ASK 继续使用自己的回复时限。
- ConversationCoordinator 负责完整话轮、本地控制/数据路由、最多6轮/8000字符上下文、真实 SSE、分句过滤、160字/400字硬上限、流式 SpeechPlayback、续听、首轮就绪后6秒、后续3秒未开口结束及5分钟会话上限。已开口允许最长30秒讲话及8秒识别宽限。超时不追加播报或反复叮声，关闭所属输入并恢复守护；用户另行开启的持续陪伴保持原开关语义。TTS 保持原语速和最多一段预合成。
- 输入窗口内的停止、取消、再见、安静、没事、不用等本地结束；底部不再显示“结束”按钮，返回键可结束当前对话或关怀（包括播放期间），菜单打开时仍优先在菜单内返回。播放中仍抑制语音识别和唤醒；不支持播放中喊“小安”打断或一口气唤醒加问句。
- 时间、有效天气、稍后、今晚晚点睡、关闭主动关怀有本地确定执行路径。聊天/故事/放松交给模型；不实现外呼、联系人通知或任意模型工具执行。
- `Conversation.start()` 仅供明确点击/调用发起会话；`Conversation.query(id, callback)`、`observe(id, callback)`、`cancel(id)` 支持 sessionId 或关联 careId。Result 区分场景、事件、状态、终止原因与有唯一 turnId 的话轮；话轮区分用户文字/原始识别片段、送播正文和实际完成播放段。取消时不将尚未完成播放的段加入已听上下文。

### 开发/未来通信调用示例

```java
// 仍使用原 Care.submit(request, listener) 取得首轮用户反馈。
Care.submit(request, result -> {
    // result.replyText / result.segments / replyIntent 来自首轮，不是 LLM 编造。
});
// 后续多轮独立关联；调用方保留 careId 或 sessionId。
Conversation.observe(request.careId, result -> {
    // 状态变化/终态；最多8个当前会话观察者，回调在主线程。
});
Conversation.query(request.careId, result -> {
    // 当前会话或持久终态；null为没有可返回结果。
    // contentStored=false时，历史查询不返回已被容量清理的原文。
});
Conversation.cancel(request.careId);
```

注意：首轮结束到建立续聊之间可能尚无关联记录。当前接口的 observe 只订阅已经存在的活动会话，不提供未来 careId 的持久订阅注册；调用方应在首轮完成后的状态更新中查询关联 session，或稍后 query。未来通信仍须遵守用户开关及原有准入，不因来自服务器放宽。
