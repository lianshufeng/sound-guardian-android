# 红糖交互延迟与资源优化计划

状态：2026-10-18已实施首轮调度、输入时序、短句缓存及初步资源准入，构建、资产、单元及相关模拟器回归通过；动态TTS延迟目标尚未达到，目标手机未连接，P0真机基线和P4真机压力验收尚未完成。实际检查与限制见[本轮验收记录](../../evaluation/interaction-performance-acceptance.md)。以下性能数值仍是目标，旧测试不作为本方案通过依据。

## 1. 从用户场景确定目标

| 使用场景 | 目标体验 | 保留的边界 |
|---|---|---|
| 喊“小糖” | 立即有表情反馈；缓存的“我在”播放时准备识别，就绪后叮一声并显示“请说话” | 提示音和最后尾音结束后才接收正文；不承诺一口气唤醒加问句 |
| 点击左上角“红糖” | 复用同一输入流程，避免重复回应和重复准备 | 未配置AI时不展示误导性的聊天就绪状态 |
| 15秒两次响指或连续片段 | 确认后立即开心，准入允许时快速播出既有话术 | 不改识别阈值、计次及去重；忙碌时不插话、不补播 |
| 聊天与续聊 | 当前话轮完成后响应并完整播报，播报结束再进入下一轮 | 每轮实际就绪后3秒未开口结束；已开口等待完整话轮及识别；生成和播报期间普通讲话不接受续说，明确“小糖”可抢占，输入窗口内重复唤醒无效 |
| 主动关怀与提醒 | 不抢用户讲话；询问完成后及时接收回复 | Care总开关、分类、安静时段、限频及一轮结果语义不变 |
| 警报或点击结束 | 及时停止当前声音，旧生成结果不再播放 | 高优先级声音守护继续；只有本地真实事件可获得安全播报资格 |
| 未来远程触发 | 与本地入口共用准入、状态、取消及结果 | 本期只设计契约，不实现服务器、推送、常连接或后台拉起 |

界面只显示准备、请说话、正在听、正在回应和结束等使用状态，不展示线程、模型加载或内存实现细节。准备失败与资源不足须有简短反馈，不能提前显示“请说话”。

## 2. 当前瓶颈及调整原则

- `GuardianService.loop()` 同时读取PCM、执行YAMNet、确认事件和定期写库。推理或数据库慢会推迟后续读取，也影响向独立KWS/VAD线程提供音频。
- KWS、VAD、SenseVoice、TTS和网络已经有各自工作线程；不是所有任务共用一个线程。需要消除跨业务等待，不能只增加线程数量。
- 唤醒流程包含600毫秒回应延迟、500毫秒尾音、150毫秒叮声和650毫秒输入等待，串行环节约1.9秒，另有“我在”播放和识别模型准备。
- 普通播报整句合成后播放，只有“我在”有缓存；TTS准备期间已抑制输入。一次性播放还占用合成工作线程。
- 流式回答已经可以播放当前段并预合成下一段，但合成若赶不上播放仍会断续；文字缓冲满时会反向等待网络读取。
- TTS和SenseVoice在节省内存模式按需加载、空闲释放，降低常驻内存，也带来冷启动成本；高性能模式加载后保留；重启和旧native调用退出同样需要计入等待。

原则：采集不等待重任务；不同能力可并行；同一个native模型仍由固定线程串行访问；统一输入、统一播报、统一资源准入。主线程保留轻量业务状态机，不承担推理、磁盘或网络工作。

## 3. 目标架构与职责

| 层次 | 职责与并发边界 | 从现有实现调整 |
|---|---|---|
| 单一PCM采集与分发 | 只读取、附加采样序号/单调时间/服务代次，并向内部有界缓冲投递；不执行推理、写库或外部回调 | 从GuardianService提取采集管线；保持唯一AudioRecord及core音频契约 |
| 声音守护 | 独立YAMNet工作器顺序处理音频窗口和EventEngine，发布确认事件 | 推理离开采集线程；规则和确认算法仍只在core |
| 唤醒与用户输入 | KWS独立；UnderstandingWorker继续分离VAD与SenseVoice；InputSessionController统一输入所有权 | 不建立第二套麦克风、识别器或业务专用SpeechInput |
| 交互会话协调 | 统一处理来源、优先级、准备、提示音、输入/输出占用和取消；状态变化串行，重任务异步 | 从GuardianService中的交互编排局部提取，复用现有Controller和Ports，避免新增第二套协调状态 |
| 关怀与聊天业务 | Care负责准入及首轮结果；Conversation负责多轮上下文、模型调用和话轮结果 | 两者调用同一交互会话协调层，不各自管理提示音和尾音 |
| 播报 | SpeechPlayback仍是唯一入口；LocalSpeechOutput内部区分控制、native合成和播放消费 | 普通播报也把播放移出合成线程；同一时间仍只有一个输出会话 |
| 资源预算 | 统一管理模型使用权、预计加载峰值、计算并发及回收，不持有页面 | 扩展ResourceBudget，供各模型持有者共同申请资源 |
| 事件存储 | 独立串行写入、批量合并同一事件的更新；存储慢不阻塞采集和告警 | 从采集循环移出EventStore.save；保留事件开始、结束及历史语义 |

“用户输入高内聚”包括麦克风话轮、点击进入、关怀回复和未来远程交互请求：入口不同，输入所有权、会话有效性、就绪提示与取消只有一套。云端模型只消费已准入的话轮，不直接操作本地设置或音频资源。

### 缓冲、过载与资源锁

- 所有音频、识别片段、待合成文字、待播放PCM和存储更新都有限额，容量和最大存活时间一并配置。现有16块音频/2个识别片段等数值先测再调，不以扩队列隐藏积压。
- 采集缓冲使用固定容量和明确所有权；若共享数组，必须用归还机制防止消费者读到已覆盖数据，不能只复用同一数组传递引用。
- 守护只保留有限待处理窗口，超载时避免追赶陈旧音频。采样序号不连续须显式重置窗口及连续证据，不把丢帧当作连续声响；实际漏检风险单列验收。
- KWS断流/丢帧重置解码器；被动陪伴可跳过过期片段，显式用户输入超载必须结束并报告，禁止静默丢字。
- 同一事件的未写更新可合并，但终态不能被覆盖成活动状态。存储队列溢出或写入失败明确上报，不阻塞麦克风，也不宣称记录成功。
- native加载、推理和释放只在所属工作器执行；不持业务锁调用native、数据库、网络或外部回调。跨工作器不形成相互等待，锁只保护短时间所有权交接。
- 初始化/释放不用可丢弃的数据队列。重复预热与回收合并为最新期望状态，保证最终关闭执行，避免控制任务无限积累；旧释放任务不能关闭新实例。

## 4. 具体优化策略

### 4.1 唤醒和输入

1. 收到有效唤醒后立即更新界面，同时申请识别准备和缓存回应播放，不再让600毫秒动画延迟阻挡音频流程。
2. 缓存回应不需要native合成，允许与ASR模型准备并行；若启动预热尚在占用资源，服从统一预算，不并行加载两个大模型。
3. 输入模型、会话所有权和采集状态均就绪后才播放叮声。合并回应与提示音之间的重复等待，只在最后一次播放后保留必要尾音。
4. 尾音先对比现有配置与100/150/250毫秒候选值，选取真机无自声误识别的最短值；不能先缩短后直接宣称安全。
5. 实际接收窗口打开时一起发布“请说话”和就绪时间，才开始3秒计时。测试接近截止时开口、长停顿、慢识别和页面重建。
6. 回答后的续听复用此流程；不重复叠加Conversation、Care和Service各自的尾音任务。关怀首轮保持其replyTimeoutMs，不误改为3秒。
7. 模型准备与输入回调绑定分离。允许预算内提前准备资源，但新输入所有者和会话代次确认后才交付就绪，避免旧播报取消或尾音回调使新准备结果失效。

### 4.2 TTS首声和连续性

1. 在同一个LocalSpeechOutput中缓存少量固定短句，先覆盖“我在”和既有响指话术；仍走SpeechPlayback、原音色和原播放器。缓存键包含文字、模型版本、音色和语速，任一变更失效。
2. 缓存优先存PCM16，初始限额为最多4条且总计不超过2MiB；按设备预算可更小。只在允许的空闲阶段补齐缓存，禁止开机批量合成所有场景话术。
3. 叮声及缓存音频走轻量准备路径，不排在旧native合成之后；播放仍由唯一输出所有者串行控制，新会话先停止旧音频。旧合成即使尚未退出，其结果也不能送播。
4. 普通播报的合成与播放解耦；native合成仍串行。流式播报最多保留当前段与一个预合成段，取消时同时撤销文字、待播PCM和所属回调。
5. 首段长度、后续段长、首段等待均在core的tts/config.json集中维护；以现有12/40字与较短首段作对照，保留自然断句、Unicode和完整正文，不把改短句当作合成吞吐率提高。
6. 保持语速0.95，不随上游速度加速。测量RTF=合成耗时/生成音频时长；若热合成RTF持续大于等于1，缓存或多线程调度不能保证长回答连续，必须继续同栈优化并如实标记不达标。
7. 用户话轮完成、网络等待期间，预算允许时提前准备TTS；回答接近结束时同样可准备下一轮ASR。仅准备资源，不提前打开输入、显示播报字幕或加载第二个实例。
8. 现有JNI回调能否提供足够细的有效PCM增量，作为条件实验验证；先测回调粒度、有限缓冲、背压、取消和native回调阻塞风险，通过后才考虑接入同一播放器。保留显式Function1<float[], Integer>签名及ProGuard约束，不把现有回调直接当成已实现音频流式播放。
9. 本期不更换TTS模型、不启用已知ARM64全NaN的INT8权重，不增加第二个合成器或播放器。后续确需换模型时另行评估契约、音质、资源及完整回归。

### 4.3 内存、性能与取消

- 将“native模型数量”“同时计算的作业数量”“缓存字节数”分别限额。一个native推理器内部可使用多个CPU线程，不把工作线程数等同于实际核占用。
- 低内存档先限定一个额外重型作业执行；普通档先用相同保守值，只有实测CPU、温度和内存均允许时才放行ASR/TTS重叠计算。YAMNet/KWS/VAD持续运行的资源须先预留。
- 加载前结合系统可用内存、低内存阈值、进程PSS、Java/native内存及该模型实测加载峰值估算余量。保留裕量，不能把总RAM或单次PSS当作不会OOM的保证。
- 节省内存保留现有10/60秒空闲释放，高性能不因空闲超时释放；交互阶段持有明确使用权，避免刚预热就被旧计时器释放。预算允许才保留热模型，压力下撤销预热、清缓存并排队释放，资源不足时明确降级。
- 低内存设备若FP32 TTS与ASR共存无法满足余量，就接受有说明的冷切换或暂时不可用，不无限重试、不同时再加载一个实例；不能把该降级算作低延迟达标。
- 每个异步任务携带服务代次、sessionId和turnId，关怀关联careId。终止首先停止可听输出并使旧结果失效；native资源在所有者线程按序释放，不要求取消API同步等待native退出。
- 点击结束、高优先级事件、替换、服务重启、配置变更和内存回收，都只取消所属会话并返回唯一终态。后续请求不得被旧失败回调关闭。

### 4.4 未来远程接入

远程网络回调只提交带来源、请求ID、有效期及交互意图的请求，不直接调用模型或播放器。关怀类请求继续走Care.submit；会话协调层负责与本地用户争用输入/输出。远程入口不因来源获得安全优先级。

契约保留去重、参数冲突、过期、忙碌、取消、结果查询和careId/sessionId关联。权限与用户授权由未来接入适配器验证，开关、安静时段及优先级仍由本地业务复核；没有运行中的服务或必要权限时返回不可用。本期只用模拟异步调用验证竞争，不建设远程通道，也不默认远程打开麦克风或上传持续倾听内容。

优先级：高优先级守护事件及用户结束先处理；用户主动交互优先于普通关怀、远程普通请求和被动拟人回应。既有安全提示资格仅由本地策略授予，关怀分类开关继续有效。

## 5. 分阶段实施与退出条件

| 阶段 | 交付 | 进入下一阶段的条件 |
|---|---|---|
| P0 基线与预算 | 在现有链路加入有界时序记录；分别测冷/热加载、推理、排队、首声、尾音及内存 | 能解释一次完整交互的耗时；不记录Token、用户正文或录音；建立目标设备预算 |
| P1 采集与存储解耦 | 独立采集/声音推理/事件写库；补齐缓冲所有权、断流和过载规则 | 模拟慢推理、慢写库时采集仍按时推进；共享确认规则、响指去重和警报优先级回归通过 |
| P2 统一交互与唤醒 | 局部提取会话协调；并行准备、合并尾音、真实就绪和统一取消；远程仅契约模拟 | 唤醒、点击、Care ASK和续聊复用输入所有权；旧回调不串会话；3秒边界正确 |
| P3 播报流水线 | 有界短句缓存、轻量提示音路径、普通播报合成/播放分离、首段与吞吐调优 | 缓存命中无需加载模型；慢合成不阻塞取消/提示控制；正文无丢失重复、字幕跟随实际播放 |
| P4 真机压力与收口 | 预算调优、全部场景矩阵、长稳、文档和APK核对 | 达到下表目标或明确列出不达标项；未验收能力不标完成 |

资源预算、取消和锁约束在每一阶段实施，P4只负责联合调优及最终压力验收。每阶段采用小改动与独立回退，不整文件重写，不一次替换全部协调器。

## 6. 验收目标与证据

以下数值是拟定目标，不是当前实测结果；P0需确定测试设备、样本、冷热条件和负载，实施阶段不得用提前显示就绪或减少识别证据来达标。

| 指标 | 初始目标与计时边界 |
|---|---|
| 视觉反馈 | 有效唤醒回调/手势到可见反馈P95不超过100毫秒 |
| 采集处理 | read返回到有界投递完成P95不超过10毫秒；不包含AudioRecord.read等待音频的时间 |
| 固定短句首声 | 请求已准入且缓存命中，到真实播放开始P95不超过250毫秒；不包含响指证据确认窗口 |
| 唤醒后可说话 | 有效唤醒回调到输入实际就绪：热会话P95不超过1.5秒；冷会话目标不超过3秒，若不能达到单列原因与缺口 |
| 用户说完到文字 | 3至6秒样本的话音结束到完整识别结果，热会话P95不超过1.5秒；包含VAD断句等待 |
| 动态播报首声 | 可形成首段的正文到首段真实播放，热会话P95不超过1秒；网络首正文与TTS冷加载另列 |
| 长回答连续性 | 热合成RTF P95争取低于0.8；段间额外空等P95不超过200毫秒，排除话术自身自然停顿 |
| 停止 | 取消请求到音频停止P95不超过150毫秒；旧native退出耗时另测，不允许旧结果恢复播放 |
| 内存与长期稳定 | 不超过P0确定的分档预算；无OOM/ANR、线程/队列/缓存无持续增长；先30分钟再2小时混合场景 |

同设备冷热分开采样，初始至少20次冷会话、50次热会话，报告中位数/P95/最大值和失败率，不只报告最快一次。记录总PSS/RSS、Java/native内存、CPU口径、队列水位、模型驻留和温度；采样峰值不能宣称绝对峰值。

业务矩阵至少包含：响指忙闲与去重、唤醒就绪和近截止开口、Care NOTICE/ASK及首轮结果、慢网络、网络快而TTS慢、长句、冷加载、取消后立即新会话、警报中断、100次启停/替换、低内存回收后重载，以及未来远程请求与本地交互竞争。特别核对自身TTS/叮声不会被当作用户输入。

验证区分确定性业务回调、数字PCM识别、真实网络和物理麦克风/实际可听输出；页面光环或播放进度不能代替声学验收。AI关闭后不得发送模型请求，远程模拟不得绕过本地开关，默认不保存用户正文和录音。

## 7. 文档与交付约束

本次已修改运行调度并同步长期规范、README及相关场景说明。已实现“我在”与响指回应有界缓存、重型作业单项许可，节省内存保留10/60秒空闲释放，高性能加载后保留；既有播报抑制不变。加载内存估计尚未结合目标手机PSS/加载峰值校准，不能视为完整内存预算验收。

实际实施新增缓存、资源职责或输入时序时，同次更新AGENTS.md、README、scenario_catalog.json及interaction/care/streaming/AI对话对应文档和调试入口；TTS参数只在core维护。新增指标按元数据有界保存，不把技术解释放进产品菜单。

每阶段运行相应用例和lint；涉及core模型、规则或共享音频契约时执行四项资产校验、两款应用构建与单元测试，并校验两款APK已启用资产SHA-256及未启用目录排除情况。沿用仓库准备脚本，不提交模型权重或凭据；最终报告逐项列出未执行、失败和未达标项。

## 8. 实施边界

- P0：加入512条有界数字元数据；目标设备冷热基线、进程/系统联合内存预算尚待采样。
- P1：唯一采集仅分发PCM，8块有界声音分支按序推理，300个ID写库分支合并；断流清连续证据，失败留元数据。慢推理、断流、慢存储纳入测试。
- P2：复用现有InputSessionController而未新增第二套协调器；取消600毫秒动画等待，移除Conversation/Care重复尾音，准备可与缓存回应重叠，保留最终650毫秒。3秒无声从实际就绪开始。远程沿用Care契约，只有业务模拟，没有网络接入。
- P3：固定短句PCM16缓存、提示音独立轻量路径、普通播报合成/播放分离；普通档网络等待时准备TTS，普通整句对话播放时准备ASR，流式回答暂不提前加载ASR以免阻塞后续段。模型加载/计算共用单项许可。暂未调短分句或尾音、未接入native PCM增量；须以RTF及真机声学结果决定后续参数实验。
- P4：两款构建、资产、94项单元测试、60项相关模拟器回归及交付19项定向复验通过，原App共享核心1项设备测试通过；动态TTS目标未达，目标ARM64手机、自声回灌、低端机OOM/温度、30分钟和2小时混合长稳尚不能标为通过。
